## 1. 目标与范围

### 1.1 系统要解决的问题

在一个或多个剑三主题的 QQ 群里，用机器人替代人工完成「开团 → 报名 → 名单确认 → 打完」这一整套组织工作。
后台负责唯一可信的数据存储，机器人负责群内交互，管理 App 负责可视化与人工兜底。

### 1.2 一期范围

**在范围内**

- 团队（`Team`）的创建、查询、解散
- 成员/报名（`Member`）的管理
- 心法词典（`bd_specialization`）的数据支撑
- 面向 QQ 机器人的 HTTP API
- 面向管理 App 的 HTTP API

**明确不在范围内**（一期）

- 群自身的管理（群列表、群名、群主、群的启用停用）——后续议题
- 管理端的权限控制（见 DR-02）
- 群与 API Key 的归属校验（见 DR-04）

### 1.3 系统上下文

    QQ 群 --群消息--> QQ 群聊机器人（外部进程，非本仓库）
                          |  HTTP: X-Api-Key + X-Group-Number + X-Operator-Qq
                          v
    管理 App --HTTP: Bearer token--> sinbot_backend --> PostgreSQL
                                                    --> Redis（登录态）

## 4. 决策记录

### 4.1 决策清单

| 编号 | 议题 | 结论 | 理由 | 影响面 |
|---|---|---|---|---|
| DR-01 | 系统边界 | 同时为 QQ 机器人与管理 App 服务；群信息管理不在一期 | 机器人是最主要入口，管理端负责人工兜底 | 接口形态、后续所有查询设计 |
| DR-02 | 管理端权限 | 登录即全权，不做 RBAC | 一期用不到，避免过度设计 | App 侧所有查询**不加群谓词**，跨群可见 |
| DR-03 | 机器人凭据 | 独立服务间凭据 `X-Api-Key`；**每个机器人实例一把独立 key**；值由配置注入（`ROBOT_API_KEYS`），**不建凭据表** | 实例数量极少，动态颁发需求不存在；分实例可单独吊销、可按 key 区分日志来源 | 需新增 `X-Api-Key` 校验通道 |
| DR-04 | 群隔离的定义 | **群隔离 = 数据分区键**，即 `group_number` 是切分数据的维度，入参给哪个群号就返回哪个群的数据。**不是访问控制** | 纠正了早期「隔离 = 授权」的误读 | API Key **不校验群范围**；所有机器人侧查询必须带群号谓词 |
| DR-05 | 是否建群表 | **不建**。`group_number` 维持为 `Team` 上的裸字符串 | 一期内群的元数据无消费方 | 见 4.2 已接受取舍 |
| DR-06 | `created_by` 语义 | 记录**群里具体操作人的 QQ 号**，既不是机器人也不是 App 账号本身 | 业务上要追溯「谁开的团」 | 该字段从「审计字段」变为「业务字段」 |
| DR-07 | `created_by` 取值范围 | 两端一致，均为 QQ 号（App 的 `username` 本身就是 QQ 号） | 值域天然统一 | **不需要**来源判别列 |
| DR-08 | 取值管道 | 机器人 → `X-Operator-Qq` 请求头；App → 从 token 解出的 `username`；两条链路在认证层合流后，**写接口在 controller 层用 `SecurityUtils.requireOperatorQq()` 取，全仓只有这一个入口**，service 只接收 `operatorQq` 入参 | 机器人已用 key 验明身份，其声明的发送人可信；App 已登录，不应由客户端再自称一次；把它做成统一入口，顺带杜绝「同一个场景两种读法读到两个值」 | `CreateTeamDTO.createdBy` 需**删除**；写接口缺操作人 → `10010 OPERATOR_QQ_MISSING` |
| DR-09 | 代理场景 | 不存在代理。团长帮别人登记时，记录的仍是**团长本人**的 QQ 号 | 确认 DR-08 中 App 走 token 推导的前提成立 | - |
| DR-10 | 成员展示方式 | 成员以 `name` 为主标识展示，QQ 号仅作标识符 | 用户区分团员靠网名而非 QQ 号 | 所有报名列表、团队详情的展示字段设计 |
| DR-11 | 审计概念的处理 | 取消独立审计语义。`BaseEntity` 的 `created_by` / `last_update_by` 即业务操作人字段 | 已**覆盖**此前「审计字段不落登录用户」的旧约定 | `AuditMetaObjectHandler` 的历史约束解除，其去留另行决定（见 OQ-06） |
| DR-12 | 索引要求 | `team.group_number` 必须建索引 | 它是全表唯一的业务过滤列，现有列表接口已按它查询 | 建表脚本 + 存量库补索引 |
| DR-13 | 「查看当前团队」判定口径 | `group_number` 相同 **且** `start_time` 晚于当前时间 | 群友关心的是「还没开的团才能报名」 | 现有 `getAvailableTeamByGroup` 语义**已正确**，只需修 P-03；历史团队需另开接口 |
| DR-14 | 结算字段的写入时机 | `locker`（黑本人）、`salary`（团队工资）**不是创建时的入参**，而是在团队过期后回填 | 开团时无法预知结果 | 创建接口不含这两个字段；需新增团队更新接口与机器人侧「设置结算」通道 |
| DR-15 | 团队编号的定义 | 编号 = 该群**招募中**团队列表按开始时间从早到晚排序后的 1-based 序号，**不额外建短号列** | 群友只需要在聊天框里输 1、2、3；代价是编号会漂 | 排序必须追加 `team_id` 升序做兜底（同 `start_time` 时保证稳定）；`team` 表不动结构 |
| DR-16 | 团队三阶段与群的可见性矩阵 | 见下方 4.5。**已开始即不可报名，且必须在服务端拦截**，不能只靠列表里看不见 | 列表不可见 ≠ 不能报名，凭记忆输编号照样能打进去 | 报名接口必须校验 `start_time > now`；结算接口必须校验 `overtime_time > now` |
| DR-17 | `overtime_time` 的业务含义 | `overtime_time - start_time` = **结算窗口时长**，当前固定 3 小时。打完 3 小时内可回填结算信息，超时该团归档 | 这让 P-02 里写死的 +3h 从「拍脑袋」变成了业务定义 | 3 小时是否可按副本配置 → OQ-05（已降级为可选项） |
| DR-18 | 报名字段的取值分工 | `member_name` ← 指令里的「id」（**游戏 ID**）；`member_qq_number` ← **当前身份的操作人 QQ**（机器人来源即 `X-Operator-Qq` 请求头，DR-08），经由 `requireOperatorQq()` 取，不由客户端传参；`specialization` / `sub_spec` ← 主副心法，**机器人侧已完成昵称到 `spec_id` 的解析，后端拿到直接落表，不做昵称匹配** | 指令只含「id 心法」两个业务参数，报名人的 QQ 只能从来源身份取 | 报名 DTO 不含 `member_qq_number`；后端不引入心法昵称→ID 的翻译逻辑，也不引入模糊查询 |
| DR-19 | 团名与副本名的关系 | `team_name` 与 `dungeon` **都保留**、**都由调用方分别录入**，服务端原样落库，**不做任何复制或推导**；当前两者取值相同只是机器人侧的结果 | 一期两者没区别，但各自保留入口，日后「同一副本开多团」只改机器人侧，后端不动 | `CreateTeamDTO` 同时收 `dungeon` 与 `team_name`；服务端不得写 `teamName = dungeon` 这类兜底 |
| DR-20 | 报名的人数约束 | 允许一人同时报多个团，**不做跨团与时间冲突检测**；单团人数上限由 `limit_method` 控制，**一期不实现** | 业务侧明确人数上限后续再做 | 一期报名接口不查已报名人数、不做任何计数校验；`limit_method` 字段保留但暂时不参与逻辑 |
| DR-21 | 报名去重规则 | 同一人（同一 QQ）对**同一个团**再次报名 → **新增一条 `member` 记录**，不是更新；但要求 `member_name` 与本人**在该团已存在的记录**不同，重复则拒绝 | 一个人可以用多个游戏角色号报同一个团；反过来同名重复没有意义 | 唯一性用**应用层查询**校验：`(team_id, member_name)` 在**未逻辑删除**的记录中必须唯一。**禁止建唯一索引**——见下方说明 |
| DR-22 | 退团 | 逻辑删除 `member`，复用 `BaseEntity` 上已有的 `@TableLogic`，MyBatis-Plus 自动过滤已退团记录 | 退团后名额要释放，同一个游戏 ID 要能重新报名 | 退团接口即 `deleteById`；**不要**改成物理删除 |
| DR-23 | 退团的时间窗口 | 与报名完全一致：**只允许在 `start_time` 之前退团**，已进入结算窗口或已归档的团队一律拒绝 | 结算依赖成员名单，开打后有人退出会让工资口径出错 | 报名与退团必须共用同一个「团队是否处于招募中」的断言，不要各写一份 `LocalDateTime.now()` 判断 |
| DR-24 | 退团指令的定位规则 | 指令形如「退团 团队编号 [id]」：`member_qq_number` 取**当前身份的操作人 QQ**（与报名同源，DR-08，不接受调用方传值）。该 QQ 在该团**只有一条**未退团记录时 `id` 可省略；有**多条**时必须给 `id` | 大部分人一个团只报一个角色，`id` 每次都输没必要 | 匹配到多条却没给 `id` → 报错要求指定；给了 `id` 却匹配不到 → 报错；一条都没有 → 报错「未报名」 |
| DR-28 | 「查看团队」的编号基准 | 编号取自**未被归档**的团队（即 `overtime_time > 当前时间`，招募中与结算窗口的并集）按 `start_time ASC, team_id ASC` 排序后的序号，而不是某一份单独的列表 | 招募期就能查到，且查看操作不因「刚开始打」而失败 | 换算在机器人侧（OQ-10），服务端不再知道「编号」这个概念，只认 `team_id`；报名/退团另行校验招募中状态 |
| DR-26 | 结算信息的写入规则 | **后端不做权限控制**，能调接口就能写，权限由机器人侧把关；**没开打不能写**（写入窗口 = 已开始且未归档，即 `start_time` ≤ now < `overtime_time`）；**写错可以随时覆盖写入**；`locker` 存**游戏 ID**（与 `member_name` 同值域），**单值**；`salary` 是**人均工资**，单位**金**，**只取整数** | 权限判断的上下文在机器人侧最完整，后端重复做一层等于把身份体系再造一遍 | 新增团队更新接口：只更新 `locker` / `salary` 两列，更新时间窗口做服务端校验；不改已有创建/删除接口的权限模型 |
| DR-27 | 心法 ID 不校验（接受风险） | 后端**不校验** `spec_id` 是否存在于 `bd_specialization`，机器人传什么落什么 | 心存洁癖想省掉一次查询 + 一个 Mapper；数据来自自家机器人 | 接受后果：脏 `spec_id` 会静默入库。日后若要加回来，只需补 `SpecializationMapper` 并在报名时做一次存在性查询（P-17 降级为「已知风险」） |
| DR-25 | 退团的幂等性 | **不幂等**：对已经退过的团再发一次「退团」，返回**错误**而非成功，提示未报名 | 报错更利于定位问题；群里重复发送属于少数情况，不值得为它牺牲可观测性 | 需要一个「未报名」语义的错误码：`ErrorCode` 目前只有团队域的 `20003` / `20004`，建议新增 `20005 MEMBER_NOT_SIGNED_UP`（或降级复用 `DATA_NOT_FOUND(20001)`） |

> **为什么 DR-21 禁止建 `(team_id, member_name)` 唯一索引**：DR-22 用逻辑删除，退团记录仍然留在表里。建了唯一索引之后，「报名 → 退团 → 同一个人用同一角色号再报名」会因为撞上那条已存在（但已退团）的记录而被数据库拒绝。唯一性只认未删除的行，这件事只能由应用层做，而应用层查询天然被 `@TableLogic` 过滤，正好符合预期。

### 4.2 DR-05 已接受的取舍

选择不建群表，意味着接受以下后果，后续若出现对应需求需重新讨论：

1. **群号无权威源**：机器人传任意群号都能建团，拼错与伪造在服务端无法发现
2. **系统无法回答「有哪些群」**：只能对 `team` 做 `DISTINCT group_number`，且得到的是无名称的数字
3. **没有停用开关**：要下线某个群，只能逐条修改团队数据

### 4.3 DR-03 / DR-08 对现有安全链的改动

`SecurityConfig` 目前只有 `/auth/login`、Druid、`/actuator/health` 放行，其余接口一律要求 Bearer 认证：

```java
.requestMatchers("/auth/login").permitAll()
.requestMatchers("/druid/**", "/error", "/actuator/health").permitAll()
.anyRequest().authenticated()
```

机器人走的是完全不同的凭据，因此需要在 Token 认证之前识别出 `X-Api-Key` 并构建机器人身份，否则会被现有 `anyRequest().authenticated()` 拦截。

**已落地**（P-06 关闭），实现要点：

```java
.addFilterBefore(robotAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)
.addFilterBefore(tokenAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)
```

| 落地项 | 位置 |
|---|---|
| key 列表（fail closed，空列表时拒绝全部机器人请求） | `RobotProperties`（`sinbot.robot.api-keys`，环境变量 `ROBOT_API_KEYS`，逗号分隔） |
| 认证明过滤器 | `RobotAuthenticationFilter`：校验 `X-Api-Key`，命中则不再走 Bearer 解析 |
| 身份建模 | principal 仍是 `LoginUser`，`username` = `X-Operator-Qq`，`roles = ["ROLE_ROBOT"]` |
| 失败出口 | 置 request 属性，由 `RestAuthenticationEntryPoint` 输出 `10009 ROBOT_API_KEY_INVALID` |

**这样做的关键收益**：`username` 被统一成 QQ 号之后，业务侧在机器人与管理端两条链路上取到的东西是同一个（DR-07），
所以 `created_by` 的填充不需要任何「按来源分支」的判断（DR-08 落地，`CreateTeamDTO.createdBy` 已删除，P-05 关闭）

**落地的收口**：走到这一步后，操作人的读取路径也一并统一了——`RobotAuthenticationFilter` 负责把 `X-Operator-Qq`
写进 `LoginUser.username`，所有写接口（创建团队 / 结算回填 / 管理端补写 / 报名 / 退团）在 controller 层统一调
`SecurityUtils.requireOperatorQq()`，service 不再触碰身份上下文。缺少操作人时统一抛 `10010`，
而不是退化为「写一条 `created_by` 为空的团」——`created_by` 是业务字段（DR-06），空值等于追责链断掉。

### 4.4 群内指令清单（当前已知）

| 指令 | 发出者 | 语义 | 后端对应能力 | 现状 |
|---|---|---|---|---|
| `创建团队 副本名称 开始时间 备注` | 团长 | 开团 | 写 `team` | 接口存在，差 `dungeon` 入参（P-01）；副本名与团名都落在调用方录入（DR-19） |
| `查看当前团队` | 群员 | 列出未开始的团 | `start_time > now` 且同群 | 接口存在，语义符合 DR-13 |
| `报名 团队编号 id 心法 [副心法]` | 群员 | 报名/报团 | 写 `member` | **完全缺失**（P-12 / P-16） |
| `退团 团队编号 [id]` | 群员 | 取消报名（限开团前） | `member` 逻辑删除 | **完全缺失**（DR-22 / DR-23 / DR-24）；`id` 在只报了一个角色时可省略 |
| `查看团队 团队编号` | 群员 | 查单个团的详情与报名名单 | 读 `team` + `member` | **完全缺失**（P-12） |
| `查询历史团队` | 群员 | 列出刚打完、待结算的团 | `start_time` ≤ 当前时间 **且** `overtime_time` > 当前时间，同群 | **完全缺失**（P-09） |
| 设置黑本人 / 团队工资 | 团长 | 回填结算信息 | 更新 `team.locker` / `team.salary` | **完全缺失**（P-10） |

群号不出现在任何指令里：机器人自己知道所在群，由请求头带入（DR-04）。
所有指令里的「团队编号」都是列表序号（DR-15），不是 `team_id`；**序号 → `team_id` 的换算在机器人侧完成**（OQ-10），
服务端接口一律接收 `team_id`，并先校验它属于请求头指定的群。

### 4.5 团队三阶段矩阵（DR-16）

| 阶段 | 时间条件 | 「查看当前团队」 | 「查询历史团队」 | 报名 | 设置结算 | App 管理端 |
|---|---|---|---|---|---|---|
| 招募中 | `start_time` > 当前时间 | 可见 | 不可见 | 允许 | 不允许 | 可见 |
| 结算窗口 | `start_time` ≤ 当前时间 < `overtime_time` | 不可见 | 可见 | **拒绝** | 允许 | 可见 |
| 归档 | `overtime_time` ≤ 当前时间 | 不可见 | 不可见 | 拒绝 | 拒绝（补结算走 App 端） | 可见，**可补写结算**（DR-26） |

三条说明：

1. 三个阶段互斥且首尾相接。上一轮担心的「进行中的团两个列表都查不到」的空档不存在——它正好是「查询历史团队」的命中区间。
2. 「历史团队」这个词容易被误读，它实际指的是**刚打完、待结算**的团队，不是远古记录。
3. 归档之后群内指令一概查不到，只能从 App 管理端看；归档不等于删除，`delete_flag` 仍是 `N`（P-15）。
4. **机器人不提供补结算**：超过结算窗口的团，群友们没办法再改结算信息，只能由 App 管理端补写。机器人侧接口维持窗口校验，管理端接口不校验窗口。

## 7. 待决问题

按依赖顺序排列，上一项未定时下一项无法定稿。

### OQ-01 · 团队生命周期 —— 已解决（DR-16）

2026-09-22 收到第一段真实业务口述，主链路已经清晰：

三阶段矩阵见 §4.5。原先「历史团队 = 过期时间晚于当前时间」的读法确实没错，是我上一轮的表格把时间轴拆错了位，更正如下：

- **招募中**（`start_time` > 当前时间）：可见于「查看当前团队」，可报名
- **结算窗口**（`start_time` ≤ 当前时间 < `overtime_time`）：可见于「查询历史团队」，可回填黑本人 / 团队工资，**不可报名**
- **归档**（`overtime_time` ≤ 当前时间）：群内指令一概查不到，只能 App 管理端看

「历史团队」这个词容易误导，它实际是**刚打完、待结算**的团队，不是远古历史。

结论不变且加强：**`Team` 不需要 `status` 字段，也不需要状态机**。三阶段的可见性与可操作性全部由两个时间字段推导。之前待补充稿里的 `RECRUITING` / `LOCKED` / `DISMISSED` 继续作废。

### OQ-02 · locker / salary 的语义 —— 基本搞清

`locker` = 黑本人，`salary` = 团队工资，都是团队结束后回填的结算字段（DR-14）。
最初「锁团 / 停止报名」的推测**作废**。剩下的细粒度问题转给 OQ-08。

### OQ-03 · limit_method —— 用途已明，细节留到后续

用途已确认：控制单团人数上限（DR-20），一期内不实现，字段保留。两个未定点：

- `limit_method` 存的到底是**人数上限本身**（如 `25`），还是某种**限制方式枚举**（由它推导出人数）？若为后者，`team` 表就读不出人数上限，报名时还得先 join 一次配置。
- 创建指令里没有这个参数，**谁、在什么时机写入**？团长报名前补一个参数，还是后台配置？

### OQ-04 · 成员与报名的关系 —— 已答大半

已定：`Member` 是**报名记录**，不是人员档案。

- 一人可报多个团，不做冲突检测（DR-20）
- 一人可在同一个团用**不同游戏 ID** 报多条（DR-21）
- 退团是逻辑删除（DR-22）

剩余一条：`member_qq_number` 与 `created_by`、`sys_user.username` 三者值域一致，天然可关联登录账号（DR-07）——这个关联要不要用起来（App 端「我报了哪些团」要不要做），还没定。

### OQ-05 · 时间与过期策略

开团时长是否固定 3 小时？是否可按副本配置？「有效团」的准确判定口径（现代码存在 P-03）。时区约定。

### OQ-06 · 时间戳字段的填充归属

`creation_date` / `last_update_date` 是否需要自动填充？当前 P-04 导致它们恒定为空。
可选方案：启用 `AuditMetaObjectHandler`（仅保留时间部分），或去掉 `fill` 让数据库默认值兜底。

### OQ-07 · 团队编号 —— 已解决（DR-15）

采用**列表序号**：招募中列表按开始时间升序的 1-based 序号。`team` 表**不加任何短号列**，也就没有跨群唯一性要考虑了，DR-05 不建群表这一点不受影响。

已接受的代价及其前提：查询列表到提交报名之间若有人新开团或有团切换阶段，编号会错位。业务侧确认该窗口内不会发生变化，后续一律遵守此前提。

三条实现约束（不照做序号就不稳定）：

1. 排序必须追加 `team_id` 升序兜底——同一 `start_time` 开的两个团，只按时间排序时先后是随机的，序号会互相漂
2. **序号 → `team_id` 的换算在机器人侧完成**，服务端不重建列表取第 N 条（OQ-10 答复）。服务端只接收 `team_id`，
   因此必须把它当**不可信输入**处理：先校验该 `team_id` 属于当前群，再校验阶段。这是唯一的越群防线
3. 逻辑删除的团由 `@TableLogic` 自动排除，不占编号（所以「解散」会重排编号，这与上面那条前提自洽）

### OQ-08 · 结算信息的写入规则 —— 已解决（DR-26）

- 权限：**后端不控制**，能调就能写，鉴权在机器人侧
- 窗口：没开打不能写
- 修改：写错了可以覆盖改写，不留版本、不留痕
- `locker`：存**游戏 ID**（不是 QQ 号），**单值**，不存在多个黑本人
- `salary`：**人均**工资，单位**金**，**只有整数**（`Integer` 够用）

- ~~归档后能否补写结算~~ —— **已答**：**机器人不提供补结算**，窗口维持不变，漏结算的团一律交给 **App 管理端**补写（§4.5 说明第 4 条）

由此产生一处**接口行为差异**，写在这里防止将来被「顺手统一」掉：同一个更新 `locker` / `salary` 的能力，机器人侧**校验窗口**（`start_time` ≤ now < `overtime_time`），管理端侧**不校验**（不受时间窗口限制，直接写）。两条链路应各自独立入口，不要做成「同一个接口加个 ignore 开关」。

### OQ-09 · team_name 怎么写进去 —— 已解决（DR-19）

结论：**两个字段都收，分别录入，赋值逻辑放在机器人侧**，服务端不参与。

- `CreateTeamDTO` 同时保留 `dungeon` 与 `team_name`
- 服务端原样落库，**不写任何 `teamName = dungeon` 的兜底或推导**
- 当前两者取值相同，是机器人侧把副本名称填进两个字段的结果，不是服务端的约定
- P-13 随之关闭：取值来源是明确的，就是机器人

一个随之而来的约束：`team_name` 现在仍标着 `@NotBlank`，机器人必须**两个字段都填**；只填 `dungeon` 会直接 400。这条要在机器人侧的对接口径里写明。

### OQ-10 · 报名指令的字段映射 —— 基本解决（DR-18）

| 指令里的东西 | 落到哪 | 怎么来 |
|---|---|---|
| `团队编号` | `team_id` | 列表序号，**机器人侧换算**（OQ-10 答复）；服务端只接收 `team_id` 并校验其属于当前群 |
| `id` | `member_name` | 游戏 ID，原样落库 |
| `心法` | `specialization` | 机器人已把昵称翻译成 `spec_id`，后端不再做匹配 |
| 副心法 | `sub_spec` | 报名时可指定，可缺省（有 `MemberMapper` 后需注意区分「未填」与「零」） |
| ——（指令里没有） | `member_qq_number` | 取当前身份的操作人 QQ（机器人来源的头是 `X-Operator-Qq`），与 `created_by` 同源（DR-08） |

顺带一条约束：`Member.specialization` 声明为 `Long` 且指向 `spec_id`，与机器人翻译成 `spec_id` 的约定对得上；但后端目前访问不了 `bd_specialization`（P-17），脏 ID 会静默入库。

剩两条转入 OQ-11：重复报名、退团。

### OQ-11 · 报名的边界

## 附录 A · sys_user 建表脚本

> 修正点：列名按 `BaseEntity` 实际字段为 `last_update_by` / `last_update_date`；
> 因 P-04，`delete_flag` 会被显式插入 `NULL`，故此处不设 `NOT NULL`（启用自动填充后可改回）。

```sql
CREATE TABLE sys_user (
    user_id          BIGINT       NOT NULL,
    username         VARCHAR(64)  NOT NULL,
    password         VARCHAR(100) NOT NULL,
    nickname         VARCHAR(64),
    role             VARCHAR(32)  NOT NULL DEFAULT 'USER',
    status           SMALLINT     NOT NULL DEFAULT 1,
    delete_flag      CHAR(1)               DEFAULT 'N',
    created_by       VARCHAR(64),
    creation_date    TIMESTAMP,
    last_update_by   VARCHAR(64),
    last_update_date TIMESTAMP,
    CONSTRAINT pk_sys_user PRIMARY KEY (user_id)
);

COMMENT ON TABLE  sys_user             IS '登录账号';
COMMENT ON COLUMN sys_user.password    IS 'BCrypt 摘要';
COMMENT ON COLUMN sys_user.username    IS 'QQ 号（DR-07，与 member_qq_number 同值域）';
COMMENT ON COLUMN sys_user.status      IS '1 启用，0 停用';
COMMENT ON COLUMN sys_user.delete_flag IS 'N 未删除 / Y 已删除';

CREATE UNIQUE INDEX uk_sys_user_username ON sys_user (username) WHERE delete_flag = 'N';
```
